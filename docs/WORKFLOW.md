# Illustration Archive - AI 开发工作流

本项目使用 AI 辅助软件开发，但需求、架构、审查、验收和最终项目所有权仍由用户掌握。

目标不是让 AI 尽可能多地生成代码。

目标是完成一个真实、可长期使用、可维护，并且用户能够理解、测试、解释，
最终可以用于 Java 后端实习简历和面试的项目。

---

## 1. 基本原则

本项目长期采用：

```text
Brain 负责思考
↓
Worker 负责实现
↓
Brain 负责审查与教学
↓
用户负责真实验收和最终决定
```

AI 可以帮助完成大量编码工作，但不能替代用户对项目的理解和控制。

项目优先级：

```text
真实需求
>
正确性
>
可测试
>
可理解
>
可维护
>
“看起来高级”
```

不为了简历堆技术。

## 2. 信息可信度与独立判断

项目中的信息来源可能互相冲突。
默认可信度顺序：

```text
当前真实仓库
↓
真实数据库 / 文件系统 / 运行结果
↓
PROJECT_STATE.md
↓
README / 其他项目文档
↓
聊天总结
↓
用户或 AI 的记忆与猜测
```

如果文档、聊天总结和真实仓库冲突：
以真实仓库为准。
Brain 必须明确指出重要差异，而不是偷偷按照旧总结继续推理。

### 独立判断原则

Brain 和 Worker 不应默认用户的想法、判断或技术方案是正确的。
当用户提出一个方案时：
1. 先根据真实需求、仓库实现和工程约束独立分析。
2. 如果方案合理，说明理由。
3. 如果存在更合理的方案，明确提出并比较取舍。
4. 如果用户的前提有误，直接指出并解释。
5. 不因为用户倾向某个答案就改变技术结论。
6. 不为了“显得高级”采用更复杂的设计。
7. 不确定时明确说明不确定，并先寻找证据或设计验证方法。
AI 的职责是帮助用户做出更好的判断，而不是附和用户。

## 3. 角色分工

### 3.1 Brain

Brain 是项目长期的大脑。
默认模型：
GPT-6 Sol，高推理
Brain 主要负责：
- 阅读真实仓库后再做技术判断
- 理解真实用户需求
- 检查相关代码、数据库迁移和测试
- 判断当前项目处于什么阶段
- 找到最小且合理的下一步
- 分析设计方案与取舍
- 控制 scope
- 定义验收标准
- 生成清晰的 Worker Prompt
- Worker 完成后检查真实 git diff
- 阅读受影响代码和测试
- 判断是否存在 Bug、设计问题或无关修改
- 带用户理解重要代码
- 指导真实环境验收
- 判断本阶段是否可以结束
- 在适当时更新 PROJECT_STATE
Brain 默认：
不直接修改业务代码。
Brain 可以：
- 阅读文件
- 搜索仓库
- 查看 Git 状态和 diff
- 阅读数据库迁移
- 阅读测试
- 运行合理的测试或验证命令
只有用户明确要求时，Brain 才直接修改业务代码。

### 3.2 Worker

Worker 是具体任务的执行者。
默认模型：
GPT-6 Luna Max
Worker 负责：
- 阅读 Brain 已批准的任务
- 阅读当前相关仓库代码
- 只实现批准范围内的内容
- 尽量复用现有项目结构和逻辑
- 添加或修改有意义的测试
- 运行相关测试和构建
- 汇报 Changed Files
- 汇报实现方式
- 汇报失败、不确定性和风险
Worker 不得：
- 自动进入下一个 feature
- 擅自扩大 scope
- 为“优化”进行无关重构
- 擅自引入新技术
- 擅自改变已经批准的架构
- 自动 commit
- 自动 push
如果任务与当前仓库冲突，或者实现过程中发现原设计存在明显问题：
停止扩大修改，并把问题交回 Brain。
不要自行重新设计整个项目。

### 3.3 用户

用户拥有最终项目控制权。
用户负责：
- 确认真实需求
- 对重大设计做最终选择
- 完成必要的真实环境验证
- 理解核心业务和重要工程决策
- 决定是否验收
- 决定是否 commit
- 决定是否进入下一阶段
以下决定不能完全交给 AI：
- 破坏性数据操作
- 核心数据模型变化
- 重要 API 行为变化
- 新基础设施
- 外部付费 API
- 项目长期方向
- 是否发布版本

## 4. 模型使用策略

默认：
Brain
→ GPT-6 Sol 高推理

明确的小功能 / 多文件修改 / 测试 / 重构
→ GPT-6 Luna Max

复杂 Bug / 事务 / 并发 / 数据一致性 / 高风险核心逻辑
→ GPT-6 Sol 高推理

Sol 多轮仍无法解决
或极高风险的独立终审
→ GPT-6 Astra
Astra 不作为日常默认模型。
模型选择应该根据任务难度，而不是为了“越强越好”。

## 5. 标准开发循环

每个有意义的功能默认遵循：

```text
1. 用户提出真实需求
        ↓
2. Brain 阅读真实仓库
        ↓
3. Brain 梳理现有调用链
        ↓
4. Brain 分析最小设计
        ↓
5. Brain 定义验收标准
        ↓
6. 用户确认重大设计
        ↓
7. Brain 生成 Worker Prompt
        ↓
8. Worker 实现
        ↓
9. Worker 运行测试并汇报修改
        ↓
10. Brain 阅读真实 git diff
        ↓
11. Brain Review
        ↓
12. 必要时 Worker 修复
        ↓
13. Brain 带用户理解关键代码
        ↓
14. 用户进行真实环境验证
        ↓
15. 用户确认验收
        ↓
16. commit
        ↓
17. 必要时更新 PROJECT_STATE
        ↓
18. 进入下一任务
```

不得直接把 `Worker：BUILD SUCCESS` 当作立刻 commit 的依据。

BUILD SUCCESS 只是证据之一，不代表功能已经完整验收。

## 6. Brain 固定输出规范

Brain 不仅需要做出正确的工程判断，还必须把结论整理成适合学习和执行的形式。
每次完成：
- 设计
- Worker Review
- Bug 调查
- 阶段验收
之后，默认按照下面的结构输出。

### 6.1 当前结论

第一部分必须直接说明当前状态。
例如：
B2｜Thumbnail Integration

✅ 真实环境验收通过
历史 backfill：total=16, ready=13, skippedGif=3, failed=0
B3 尚未开始
或者：
❌ 当前不能验收
原因：存在数据库与文件系统状态不一致风险
不要让用户从几百字分析里自己猜结论。

### 6.2 这一轮实际发生了什么

只总结最重要的 3～5 个变化。
不要重新总结整个项目历史。
例如：
新 JPG/PNG 导入后生成 thumbnail
GIF 继续使用原图
thumbnail 失败不影响核心归档
增加历史 thumbnail backfill
已有 thumbnail 会复用

### 6.3 哪些已经证明，哪些还没有证明

必须区分：
✅ 代码结构已确认
✅ 自动化测试已覆盖
✅ 构建通过

按当前阶段列出尚未验证的项目；例如 B2 已通过真实 MySQL 与文件系统验收，B3 的浏览器验证尚未开始。
不要把：
测试通过
自动解释成：
整个功能已经完全正确

### 6.4 这一轮用户必须理解什么

每轮最多选择 2～4 个真正重要的知识点。
优先：
- 业务规则
- 数据流
- 事务边界
- 数据库与文件系统一致性
- 异常处理
- 补偿逻辑
- 幂等性
- 并发
- 数据建模
- API 语义
- 性能敏感逻辑
- 重要架构决定
必要时让用户先用自己的话解释，再进行纠正。

### 6.5 用户现在只做什么

一次默认只给 1～3 个操作。
必须同时告诉用户：
做什么
为什么做
成功应该看到什么
例如：
现在只做：

1. 导入一张新的 JPG。
2. 检查 originals 与 thumbnails。
3. 把结果告诉我。

成功应该看到：

2026-09/...jpg              ✅
thumbnails/2026-09/...jpg   ✅
数据库记录                  ✅
完成后再进入下一批验证。
不要一次抛十几个操作。

### 6.6 当前小阶段完成标准

说明当前小阶段是否已满足验收条件。B2 已完成真实环境验收；完成 B2 不会自动启动 B3，下一阶段仍需用户明确提出。

## 7. Review 检查清单

Brain 在批准 Worker 修改前，至少考虑：
- 是否满足原始验收标准
- 是否存在无关修改
- 是否重复实现已有逻辑
- 是否合理复用了现有代码
- 异常路径是否正确
- 清理和补偿路径是否正确
- 事务边界是否正确
- 数据库和文件系统是否可能不一致
- 是否存在并发问题
- 是否存在幂等问题
- 测试是否真的验证业务，而不是为了通过而写
- 是否出现无意义抽象
- Worker 是否偷偷扩大 scope
- 是否改变了 API 或数据模型
- 用户是否能够解释核心设计
如果不确定：
调查，而不是猜。

## 8. 教学规则

用户正在学习 Java 后端开发。
目标不是把所有 AI 生成的代码逐行背下来。
目标是逐渐取得对项目核心部分的所有权。
对于重要代码，Brain 应解释：
1. 这段东西为什么存在。
2. 数据从哪里进入。
3. 主要调用链是什么。
4. 正常路径是什么。
5. 失败路径是什么。
6. 为什么选择当前设计。
7. 如果需求变化，哪里需要修改。

### 高学习优先级

必须逐渐理解：
- 核心业务规则
- Controller / Service / Repository 分层
- 数据模型
- 数据库行为
- SQL
- 事务
- 文件与数据库一致性
- 异常处理
- HTTP / REST 语义
- 并发相关逻辑
- 幂等性
- 数据迁移
- 历史数据处理
- 性能敏感路径
- 重要测试设计

### 中等优先级

理解作用和基本使用方式即可：
- Spring Boot 框架整合
- Java 常用 API
- 图片处理 API
- Maven
- Flyway
- 测试框架
- 配置系统

### 低优先级

通常不逐行学习：
- DTO getter / setter
- 重复 mapping
- 机械 CRUD
- 简单 HTML / CSS
- 简单前端绑定
- 重复测试初始化
- 明显样板代码
这些内容可以由 AI 大量辅助完成。

## 9. Scope 控制

不得因为招聘 JD 中出现某项技术，就自动加入项目。
以下技术必须先出现真实需求：
- Redis
- MQ
- Elasticsearch
- 微服务
- 对象存储
- 登录 / 权限
- OCR
- AI 翻译
- X integration
- 其他外部服务
默认原则：
先解决真实问题
↓
再判断当前设计是否真的遇到瓶颈
↓
最后才考虑引入新技术
不要反过来：
我想写 Redis 到简历
↓
所以找个地方硬塞 Redis

## 10. 必须由用户确认的重要变更

涉及以下内容时，Brain 必须暂停并征求用户确认：
- 数据库 schema 的重大变化
- destructive migration
- 删除或覆盖真实用户媒体
- 事务语义变化
- 公共 API 行为变化
- 核心数据模型变化
- 引入新基础设施
- 登录与权限
- 外部付费 API
- 大规模架构重写
- 不可逆的数据操作
AI 不独立做不可逆项目决定。

## 11. 验证规则

验证方式必须匹配实际 feature。
可能包括：
- 自动化测试
- Maven test / package
- HTTP 请求
- 浏览器行为
- MySQL / Navicat 检查
- 文件系统检查
- 故意触发异常
- 重复执行验证幂等性
- 应用重启验证
- 历史数据验证
Brain 应告诉用户：
为什么这次需要这个验证
而不是机械地让用户执行命令。

## 12. Commit 规则

只有满足：
实现完成
+
Brain Review
+
用户理解核心部分
+
真实验证完成
+
用户确认
以后才 commit。
AI 默认不得自动 commit 或 push。

## 13. PROJECT_STATE 的职责

docs/PROJECT_STATE.md 记录：
现在正在做哪个版本
这个版本的目标是什么
版本做到什么才算完成
当前完成了哪些阶段
当前正在做什么
下一步是什么
已经确定的重要设计
明确不在当前版本做什么
它不是详细 changelog。
详细实现历史由 Git 负责。
Brain 每次开始一个新的长期上下文时，应优先阅读：
AGENTS.md
docs/PROJECT_STATE.md
docs/WORKFLOW.md
然后再检查真实仓库。

## 14. 版本边界

每一个版本在开始时必须定义：
Version Goal
Scope
Definition of Done
Out of Scope
不能只写：
V0.2
却没有说明 V0.2 做到哪里结束。
开发过程中可以调整版本范围，但重大范围变化必须由用户确认，
并同步更新 PROJECT_STATE。

## 15. Brain / Worker 对话生命周期

### Brain

一个 Brain 默认对应一个版本。
例如：
Brain | Illustration Archive V0.2
负责整个 V0.2。
只要：
- 仍然处于 V0.2
- PROJECT_STATE 正常维护
- Brain 能正确读取真实仓库
- 没有明显持续遗忘或逻辑漂移
就没有必要因为对话变长而频繁重开 Brain。
V0.2 完成以后：
更新 PROJECT_STATE
↓
完成 V0.2 阶段总结
↓
必要时发布 / tag
↓
关闭 V0.2 Brain
↓
新开 Brain | Illustration Archive V0.3

### Worker

Worker 生命周期比 Brain 短。
默认：
一个独立 feature / 一个清晰工作包
=
一个 Worker 对话
例如：
Worker | B2 Thumbnail Integration
B2 没验收之前：
继续使用同一个 B2 Worker 修复问题。
B2 完成以后：
不继续让它写 B3。
应该新开：
Worker | B3 Thumbnail HTTP & Gallery
这样可以减少上下文污染。

## 16. 什么时候提前更换 Brain

以下情况之一出现时，可以提前开启新的 Brain：
- 已跨越版本边界
- 当前 Brain 多次误解已经确定的项目状态
- 已经无法稳定区分完成 / 未完成内容
- 多次重复提出已经否决的方案
- 明显依赖很早的聊天记忆，而不是读取真实仓库
- PROJECT_STATE 与 Brain 的理解长期不一致
- 一个版本异常巨大，已经包含多个独立大阶段
- 用户发现对话已经明显影响理解或效率
不要仅仅因为发生一次上下文压缩就立即更换 Brain。

## 17. 新 Brain 交接规则

新 Brain 不依赖旧 Brain 的完整聊天记录。
首先读取：
AGENTS.md
docs/PROJECT_STATE.md
docs/WORKFLOW.md
Git history
当前代码
相关测试
然后确认：
项目现在是什么
上一阶段完成了什么
当前正在做什么
下一步是什么
有哪些重要设计约束
旧聊天只能作为辅助信息。

## 18. 阶段结束复盘

每完成一个主要阶段，Brain 给出一份简短复盘：
1. 这一阶段解决了什么问题？
2. 数据 / 控制流现在怎么走？
3. 最重要的 2～3 个设计决定是什么？
4. 用户新学到了什么？
5. 哪些实现细节不需要记忆？
6. 用户现在应该能够解释什么？
7. 下一阶段是什么？
尽量控制在一屏左右。

## 19. 版本结束与总路线交接

一个版本完成以后，Brain 额外生成一份：
Milestone Handoff Summary
用于用户带回长期学习路线聊天。
内容包括：
项目：
Illustration Archive

完成版本：
Vx.x

本版本解决的问题：

完成的主要功能：

真正使用到的 Java / Spring / MySQL / 工程知识：

用户目前可以解释的核心设计：

仍然薄弱的知识：

当前项目成熟度：

下一版本计划：

当前实习准备主线建议：
这份总结用于长期路线判断。
它不是 README，也不是 PROJECT_STATE 的替代品。

## 20. 最终原则

AI 的价值不是代替用户拥有项目。
正确的长期状态应该是：
需求是用户的
设计用户能解释
代码可以大量由 AI 辅助
关键 diff 用户看得懂
失败路径用户知道
真实结果用户验证过
项目历史由 Git 记录
AI 随时可以换
项目知识不会随着聊天一起消失
